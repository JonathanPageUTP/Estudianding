02

Vulnerabilidad vs Amenaza vs Riesgo

🐛 Vulnerabilidad

Debilidad en un sistema que puede ser explotada.

Ej: SQL Injection en formulario de login sin prepared statements

SELECT * FROM users WHERE user = '$input'

🥷 Amenaza

Agente que puede explotar una vulnerabilidad.

Actores: Cibercriminal, Bot automatizado, Insider malicioso

Ej: Script masivo buscando formularios vulnerables a SQLi

⚠ Riesgo

Probabilidad de que una amenaza explote una vulnerabilidad.

Riesgo = Amenaza × Vulnerabilidad × Impacto

📌 Ejemplo Aplicado — E-commerce

Checkout sin validación → Script automatizado SQLi → 70% prob. de compromiso de 50K tarjetas → $2.5M multas PCI DSS

Tríada CIA — Pilares de la Seguridad

🔒

Confidencialidad

Información accesible solo a usuarios autorizados

  • Datos de tarjetas encriptados
  • Información personal de clientes
  • Credenciales de acceso seguras
  • Datos financieros internos
Encriptación · Control de acceso

🛡

Integridad

Información no alterada de manera no autorizada

  • Precios de productos sin manipular
  • Órdenes de compra exactas
  • Logs de auditoría inmutables
  • Código de aplicación verificado
Hashing · Firmas digitales

⏱️

Disponibilidad

Sistemas accesibles cuando se necesiten

  • Sitio web funcionando 24/7
  • Procesamiento de pagos activo
  • Base de datos accesible
  • APIs respondiendo correctamente
Redundancia · Backups · Anti-DDoS

💰 Impacto Económico de Violaciones CIA

Confidencialidad → Multas PCI DSS $5K–$100K/mes · Integridad → Manipulación de precios = pérdidas directas · Disponibilidad → 1h downtime = $100K–$300K en ventas perdidas

04

Autenticación vs Autorización

🔍

Autenticación

"¿Quién eres?"

Verifica la identidad de un usuario antes de permitir acceso.

Sabes Contraseña, PIN, Pregunta de seguridad
Tienes Teléfono (SMS), Token hardware, TOTP
Eres Huella dactilar, Facial, Iris
🔑

Autorización

"¿Qué puedes hacer?"

Determina qué puede hacer un usuario ya autenticado.

Cliente Ver sus pedidos, actualizar perfil, comprar
Vendedor Ver sus productos, actualizar inventario, devoluciones
Admin Gestionar todos los pedidos, productos, reportes

🧠 Diferencia clave

La autenticación responde ¿Quién? y ocurre primero. La autorización responde ¿Qué puede? y ocurre después. Un sistema puede autenticar correctamente y aun así tener fallas de autorización (Broken Access Control — OWASP A01).

05

Encriptación vs Hashing

🔒 Encriptación — Proceso Reversible

Requiere una clave para cifrar y descifrar. Los datos son recuperables.

// Texto plano: "4532-1234-5678-9012" → AES-256 → "A7B9C1D3E5F7..." (cifrado) ← con clave ← "4532-1234-5678-9012" (recuperado)

Casos de uso:

  • Tarjetas de crédito en DB
  • Información personal sensible
  • Comunicación HTTPS
AES-256 RSA TLS 1.3

🔴 Hashing — Función de Una Vía

Sin clave, proceso irreversible. Siempre produce salida de longitud fija.

// Password: "MiPassword123" → bcrypt(12 rounds) → "$2b$12$LQv3c1..." // ← IRREVERSIBLE

Casos de uso:

  • Almacenar contraseñas
  • Verificar integridad
  • Tokens de sesión
bcrypt SHA-256 Argon2

📌 Regla de Oro

Usa encriptación cuando necesites recuperar el dato original (tarjetas, PII). Usa hashing cuando solo necesitas verificar sin recuperar (contraseñas). Nunca guardes contraseñas con MD5 o SHA1 — usa bcrypt con mínimo 12 rounds.

06

Principios Fundamentales de Seguridad

🛡️

Defense in Depth

Múltiples capas independientes de protección.

  • Firewall + WAF + IDS
  • Auth + Authz + Auditoría
  • Si una capa falla, otras protegen
🔏

Least Privilege

Acceso mínimo necesario para cada entidad.

  • Usuarios: Solo sus datos
  • Apps: Permisos específicos
  • Servicios: Recursos mínimos
🚨

Fail Secure

Fallo en modo seguro: denegar por defecto.

  • Error DB → Denegar acceso
  • Falla auth → Logout
  • Red caída → Offline seguro
🏗️

Security by Design

Seguridad integrada desde el inicio del diseño.

  • Threat modeling desde inicio
  • Arquitectura con seg. integrada
  • No como "add-on" posterior

10

Card Testing / Carding

⚠ Definición

Técnica automatizada donde cibercriminales prueban la validez de números de tarjetas robadas usando bots para realizar transacciones pequeñas ($1–$5 USD) en sitios e-commerce.

Anatomía del Ataque

1
Obtención de datos
Dark web, data breaches, skimming, phishing
2
Preparación
Bots (SentryMBA, STORM), proxy chains, user agents variables
3
Ejecución
100–1000 micro-transacciones/min, rotación de IPs
4
Monetización
$1–3 tarjeta básica · $10–50 premium · $100+ "fullz"

Impacto Financiero

ConceptoCosto
Chargeback fees $15–25 / transacción
Processing fees $0.30–0.50 / intento
Daño reputacional $50K–100K anuales
Investigación fraude $25–50 / caso

📊 Estadísticas

  • $28 billones en pérdidas globales (2023)
  • 65% de sitios sufren card testing mensualmente
  • 15–20% de tarjetas probadas resultan válidas

Técnicas de Mitigación

⏱ Rate Limiting

Máx. 3 intentos de pago / 15 min por IP

🤖 CAPTCHA Inteligente

reCAPTCHA v3 si risk score > 0.7

🔐 3D Secure 2.0

Autenticación adicional por el emisor

🖥 Device Fingerprinting

User-agent, timezone, canvas hash

🌐 IP Reputation

Bloquear proxies, Tor, IPs con riskScore > 80

📊 Behavioral Analytics

checkoutTime < 30s, amount < $10, geoAnomaly

Account Takeover (ATO)

22%
Aumento en ataques ATO (2023)
$120
Pérdida promedio por cuenta comprometida

Métodos de Ataque

🔓
Credential Stuffing
Usar credenciales de otros breaches. 80% de usuarios reutilizan passwords.
🔑
Password Spraying
Probar contraseñas comunes contra muchas cuentas a baja velocidad para evadir bloqueos.
🍪
Session Hijacking
Robar tokens de sesión JWT/Cookie para suplantar la sesión activa del usuario.
📱
SIM Swapping
Bypass de 2FA por SMS convenciendo a la operadora de reasignar el número.
🎣
Phishing
Páginas falsas idénticas al sitio legítimo para capturar credenciales en tiempo real.
🦠
Malware
Keyloggers e info-stealers que capturan credenciales directamente del dispositivo.

Indicadores de ATO

Categoría Señales de Alerta
Geográfico Login desde país diferente, múltiples países en 1 hora
Temporal Fuera del horario habitual, inactividad prolongada + burst repentino
Comportamiento Cambio de dirección de envío, nuevos métodos de pago, uso de puntos
Dispositivo Dispositivo desconocido, VPN/proxy, múltiples fallos seguidos de éxito

Digital Skimming — Magecart

⚠ ¿Qué es?

Inyección de JavaScript malicioso en páginas de checkout que captura datos de tarjetas en tiempo real, sin interferir con la transacción normal. Extremadamente difícil de detectar.

Víctimas Notables

British Airways 2018

380K tarjetas comprometidas

Ticketmaster 2018

40K tarjetas, activo meses

Newegg 2018

1 mes activo sin detección

Contramedidas

🔒
Content Security Policy (CSP)
Controlar mediante cabeceras HTTP qué scripts tienen permitida su ejecución.
🔏
Subresource Integrity (SRI)
Verificar el hash criptográfico de cada script externo antes de ejecutarlo.
👁
Runtime Script Monitoring
Usar MutationObserver en el DOM para detectar scripts inyectados dinámicamente.
📁
File Integrity Monitoring
Detectar cambios no autorizados en archivos JS/HTML del servidor.

Resumen — Métricas Clave de Seguridad E-Commerce

✅ Checklist de Implementación

  • Todas las contraseñas con bcrypt / Argon2 (saltRounds ≥ 12)
  • HTTPS en toda la aplicación (HSTS habilitado)
  • Datos sensibles encriptados en base de datos (AES-256)
  • Rate limiting en login y checkout (máx. 3–5 intentos)
  • MFA obligatorio para cuentas con métodos de pago
  • WAF configurado con reglas anti-SQLi y XSS
  • Content Security Policy (CSP) en todas las páginas
  • Subresource Integrity (SRI) para scripts externos
  • Logs de auditoría inmutables para acciones sensibles
  • Monitoreo de breaches con HaveIBeenPwned

🧠 Principio de Oro para Recordar

La seguridad en e-commerce no es un producto que se instala, es un proceso continuo. Aplica Defense in Depth: si una capa falla, la siguiente detiene el ataque. Mide, monitorea y mejora constantemente usando los KPIs como guía objetiva.
